# Connected accounts

Open the sample inbox's folder button, then **Accounts**. IMAP is selected by default. Enter the server hostname (for example `imap.example.com`), TLS port (usually `993`), email address, login name, and password or app password, then press **Connect**. Select the saved account, open a mailbox, and tap a message to read it. Refresh and Load more fetch current server data. IMAP supports reading, read/unread changes and stars; opening a message uses `BODY.PEEK[]` and does not mark it read.

For JMAP, select **JMAP**, enter the HTTPS session address and access token supplied by your provider, and press **Connect**. Choose an account if the server returns more than one. JMAP currently requires same-origin session/API endpoints.

IMAP uses implicit TLS with certificate-chain, hostname and app pin verification through the original Swift client and HarmonyOS trust configuration. STARTTLS, OAuth sign-in and SMTP sending remain unfinished. Provider interoperability has only been tested with synthetic local servers. A rejected credential can be replaced by disconnecting the local account and adding it again. JMAP tokens are limited to 1024 UTF-8 bytes; IMAP usernames to 512 and passwords to 1024. The username/password pair is encoded for storage in Asset Store, not placed in the account database.

Connected mail is separate from the offline sample mailbox. Opening a message does not automatically mark it read. Use the reader's native toolbar to add/remove a star or mark it read/unread. These actions change the server message. Sending, general folder moves, attachments and HTML rendering are not yet connected to live accounts. Previously fetched lists and opened bodies are available as timestamped saved copies when the server is unavailable; see [offline caching](cache.md). A missing plain-text body or incomplete body is explicitly identified in the reader.

The toolbar respects the account’s read-only status. JMAP requires rights in every mailbox the message belongs to; IMAP uses the selected mailbox’s READ-ONLY and PERMANENTFLAGS response and rechecks it before each write. Each action patches only its selected keyword, preserving unrelated flags and mailbox membership. The app reloads the message and mailbox counts after acknowledgement. It does not optimistically show an unconfirmed change or retry a write automatically. If the connection drops, Refresh retrieves the current message before another action is enabled. Returning to the message list refreshes its query after an attempted change.

Archive moves an Inbox message into the mailbox with the server's Archive role. Existing labels and other memberships remain intact. If the message already belongs to Archive, only its Inbox membership is removed. The action is disabled when the server does not provide the required roles or permissions.

After the server acknowledges Archive, the app returns to the refreshed message list with an Undo button. Undo reverses only the membership changes made by that action. It refetches the message and refuses to overwrite later mailbox changes; an atomic server-state precondition also catches changes between checking and writing. Concurrent keyword changes are preserved. Undo is available for the latest acknowledged archive within the current mailbox session; it is not persisted across app restarts. An unconfirmed archive or undo is never automatically replayed.

## Storage

`AccountStore.ets` keeps account IDs, display names and session addresses in `thunderbird_accounts.db`, using RDB encryption and security level S3. Schema version 4 also adds encrypted local outgoing drafts; SMTP settings use separate Asset Store entries. Schema version 3 added an explicit email_address column alongside the encrypted, account-scoped mail cache introduced in version 2. It migrates versions 1 and 2 without replacing account records or credentials. Existing accounts receive an empty email identity, because a login name must not be assumed to be an email address. A newer unknown schema is rejected without resetting it.

Credentials are stored separately using HarmonyOS Asset Store with `DEVICE_UNLOCKED` accessibility and `SyncType.NEVER`. They are not included in database rows, preferences, logs or screenshots. The asset's default uninstall behavior is retained; the app does not request permission to preserve credentials after uninstall. The input field disables autofill and is cleared after saving or leaving the account workspace. JavaScript strings cannot be reliably zeroed; temporary byte buffers are cleared after use.

Registration writes a pending metadata row before creating its credential, then marks the row ready. Removal marks the row deleting, removes the credential and cached mail, then deletes the row. On reopening, interrupted rows are cleaned up through the same removal path. This makes the two-store operation recoverable without pretending it is one atomic transaction. Storage errors do not silently fall back to plaintext tokens.

Disconnect asks for confirmation in the app and removes this device's saved account, token and cached mail. Server mail remains untouched.

## Verification

The email address and login name are independent: for example, `reader@example.test` can use login `account`. The email address becomes the displayed account identity and is saved in encrypted metadata. Only the login name and password are used for IMAP authentication and retained together in Asset Store. New IMAP setup validates the email address with Thunderbird’s original EmailAddress code. Sending is still unfinished, so this does not claim a verified SMTP sender identity.

The production IMAP test HAP includes the same native core and account/storage/UI code as the mail app. Its fourteen account tests verify TLS login and rejection, plain LIST fallback, 50-message paging, UIDVALIDITY safety, missing/mismatched messages, secure credential persistence, separate email/login values, version-2 migration, flag permission checks, lost or rejected STORE replies, and reading/star changes after the screen is recreated. Nine direct original-client tests and all 13 original body fixtures also pass. Run `scripts/test-mail-core build` with the emulator stopped, then `scripts/test-mail-core device`; the latter runs the complete 76-check batch and stops the emulator on exit. See [IMAP implementation and limits](native-imap.md).


`./scripts/test-device build` prepares the historical tests with the emulator off; `./scripts/test-device device` starts it, runs 15 tests and stops it on exit: nine native JMAP/HTTP checks (including backend draft creation), five account/cache-storage checks, and an account UI flow. The UI test uses a separately compiled test page with a prefilled synthetic server/token and an injected test-only client factory and loopback transport. It presses Connect, verifies the token field clears, opens the saved account and Inbox, and asserts the fetched message body. It then exercises read/unread and star/unstar, simulates a lost acknowledgement after the server applies a star, refreshes to recover, then archives the message and undoes it. The test verifies disappearance from Inbox and restoration of the starred row. Fixture-side checks verify the exact patches, preserved label membership and absence of replay. It then makes the fixture unavailable, restarts the test ability, reopens the saved account, and reads the cached message with all three server actions disabled. Restoring the fixture and pressing Refresh removes the saved-copy label and re-enables those actions. The test account, cached mail and credentials are removed afterward.

Storage tests reopen the encrypted database, retrieve the credential through Asset Store, remove both, recover an interrupted registration, and reject oversized tokens before creating a row. Cache checks also verify persistence after closing/reopening storage, account isolation, dirty-record filtering, membership reconciliation, physical removal of account cache rows, prevention of late writes after removal, and migration from schema 1. The tests use dedicated test databases and do not reset the sample mailbox or real account database.

The test runner enables the platform's documented UI-test mode temporarily and restores an observed enabled setting on exit; otherwise it requests disabled mode. The emulator sometimes cannot read the parameter, so independent verification of its final value is not claimed. No real provider credentials or messages have been used. Interactive keyboard entry, real-provider interoperability, locked-device behavior and full accessibility validation remain pending.
